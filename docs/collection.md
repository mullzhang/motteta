# Codexによる履歴取得

Codexがブラウザで購入履歴を読み取り、共通のJSONへまとめてCLIに渡します。
普段の取り込みの依頼例は[README](../README.md#購入履歴をまとめて取り込む)を参照してください。
この文書では、取得処理を調整する際の判断基準と、入力データを作る際の扱いを説明します。

## 利用者から受け取る情報

通常の依頼では、購入先と対象期間だけを受け取ります。
Codexが接続済みのChromeを使い、購入先を開いて対象の購入履歴や購入済み一覧へ移動します。
ブラウザや紙と電子の対象が明示されている場合は、その指定を優先します。

既存の台帳と購入先ごとのアカウント識別名を再利用します。
新しいアカウントが一意に決まる場合はCodexが識別名を付け、別のアカウントと区別できない場合だけ利用者へ確認します。
ログイン、追加認証、実際のアクセス許可が必要になった場合は、その時点で必要な操作を利用者へ案内します。

登録データの作成、既存記録との照合、取り込み、結果の報告はCodexが行います。
出力はCodexがリポジトリの外へ保存します。
再開しやすい期間と注文数で区切り、取得明細だけでなく取得範囲と中断理由も記録します。
型と状態の詳細は[入力契約](contracts.md)を参照してください。

完了、中断、失敗のいずれでも、最終報告前に作業用タブを閉じて確認します。
再開に必要な情報はファイルへ保存します。

## 購入先ごとの確認

| 対象 | 確認する内容 |
| --- | --- |
| Amazon.co.jp | 注文番号、注文内で安定した明細の識別子、書籍と数量、日付、注文状態。ASINの名前空間は `amazon`、対象市場は `amazon.co.jp`。 |
| 楽天ブックス | 書籍の注文と明細、商品URLと商品ID、日付と状態。商品IDは `rakuten-books` と `books.rakuten.co.jp` の組み合わせで記録する。 |
| 楽天市場の書店 | 注文番号だけでなくショップと明細を確認する。商品IDの範囲は `item.rakuten.co.jp/ショップID` とし、ショップごとの画面差を残す。 |
| [O’Reilly Japan Ebook Store](collection/oreilly.md) | 購入済み一覧へ移動し、電子書籍を記録する。定額学習サービスは対象に含めない。 |
| [Gihyo Digital Publishing](collection/gihyo.md) | マイページの購入済み一覧を使う。PDFとEPUBは同じ入手にまとめ、Gihyo Directとは履歴を分ける。 |
| [SEshop](collection/seshop.md) | 発送前と発送後の注文、および電子書籍の一覧を確認し、同じ購入の情報をまとめる。 |
| その他のサービス | 自由な `source` を使い、同じJSON形式へ変換する。購入の事実と書誌情報の参照先を分ける。 |

「楽天」の依頼は、楽天ブックスと楽天市場の書籍の購入履歴を対象とし、楽天Koboを含めません。

紙、電子、版、巻を確認し、分からなければ不明にします。
読み取り先は、Codexが実際の画面で確認します。

## 購入済み一覧と取得範囲

購入済みの本の一覧と、取引ごとの購入履歴を区別します。
根拠には、観測した一覧の安定した参照先と日時を記録します。

| 確認できた根拠 | 入力への反映 |
| --- | --- |
| 注文や購入済み一覧で購入の事実が分かる | `acquisition_kind: purchase`。注文状態は表示から分かる値を使い、不明なら `unknown`。 |
| 所持や利用権だけが分かり、購入とは断定できない | `ownership_assertion` とし、`order_state: null`。 |
| 購入日が分からない | `acquired_on: null`。現在の所持状態も、根拠がなければ `unknown`。 |
| PDFとEPUBなど複数形式が同じ入手で使える | 一つの入手記録の `book.file_formats` にまとめる。 |

`book.file_formats` の入力値は小文字の `pdf`、`epub`、`mobi`、`other` です。
画面上の「PDF」「EPUB」は、それぞれ `pdf` と `epub` に対応付けます。

日付範囲が指定されている場合、購入日が分かる項目、または画面の期間フィルターなどで対象期間内だと確認できた項目を取り込みます。
期間内か判断できない項目は `coverage.unverified` へ残し、書名と参照先を再開情報へ記録します。

「全期間」の場合は、購入日が不明な購入済み項目も対象です。
現在の入力形式は日付範囲が必須なので、`coverage.requested_start: "0001-01-01"`、`requested_end` は利用者のタイムゾーンでの当日とします。
この下限値は無期限の指定を表します。
期間内の入手の網羅を確認できなければ、`status: partial` として未確認の内容を残します。
確認済みの日付範囲も不明なら `checked_start` と `checked_end` は両方 `null` にします。

## 入手の識別と再取り込み

購入済み一覧で、アカウント内の入手や利用権に対応する安定したIDを確認できた場合だけ `external.holding_id` を使います。
商品ID、ISBN、表示順、形式ごとのリンクを入手のIDへ読み替えません。
再取り込みでは、既存記録と同じ購入先、アカウント、入手のキーを使います。
追加で見つけたIDは根拠の注記へ残し、既存購入との対応を確認して扱います。
注文と明細が確認できる場合は、その組み合わせを使います。

注文内の商品と形態から一意性を確認した場合は、`external.derived_identity` に生成規則と根拠を記録します。
注文全体の購入明細を確認したか、同じ商品IDと形態に対応する明細が何件あるか、日時、参照先、確認方法を残します。
画像リンクと書名リンクが同じ明細に属する場合は一件と数えます。
注文全体を確認でき、対応明細が一件の場合だけ派生キーを使用できます。詳しい形式は[入力契約](contracts.md#明細idがない注文の派生キー)を参照してください。
判断できないものは明細の識別情報を不明のまま渡し、確認対象として残します。

## 数量の扱い

利用者から別の方針が指定されていなければ、数量が不明な本は既定で `quantity: 1` とします。
明示された数量、現在の画面で確認済みの数量、同じ購入の既存記録で分かっている数量は、そのまま保持します。
既定の扱いで補った数量は根拠の注記に残します。

## 再開と継続更新

新しい注文が追加されるとページ位置が変わるため、日付と注文番号を使って再開します。
前回と重なる範囲から取得しても、安定した購入の識別子が同じなら同じ記録へ反映します。
同じ取得を再送する場合は `import_id` とJSONを変えず、新しい観測として取得し直した場合は新しい `import_id` を使います。
派生キーを使う新しい観測では、注文全体と対応明細の一意性を再確認します。
今回の購入履歴の根拠と同じ日時・参照先で記録してください。
既存の購入を明細ID不明のまま確定済みの場合は、その購入と一致することを確認して `bind-identity` で関連付けます。
取り込みで候補付きの `missing_identity` になった場合は、`same_acquisition` に既存購入IDを指定して関連付けます。

予約中や注文中の明細も再確認します。
見つからなかったことを理由に、キャンセルや削除を推定しません。
認証、アクセス制限、Codexの利用枠などで中断した場合は `coverage.status` を `partial` または `failed` とし、未確認箇所と再開情報を残します。

## 取り込み後

保存前に確認する場合は `motteta import <history.json> --dry-run --json` を使います。
作成や確認対象の見込みを返します。

CLIの作成、更新、既存、確認対象の件数と取得範囲を確認します。
終了コード3の場合は、何が保存され、何が未確認なのかを報告します。
